---
name: setup
description: Writes the wiring of the plugin celetis into a product project. Only a human starts it.
disable-model-invocation: true
---

**Celetis entry.** Before any step or response, including commentary or an announcement, bind `<plugin>` to the absolute prefix before `/skills/<name>/SKILL.md` in the path of this loaded file. Then read `<plugin>/docs/procedures/entry.md` whole, in one read, and follow it before any product-path scan. Do this on each invocation, including a same-session handoff.

The session holds setup approval; `celetis --agent <host> setup <sub-command>` makes each project change.
Setup approval does not approve a plugin update. The entry contract owns the read-only update
check. One affirmative response in an interactive terminal, or a person's direct click on the
board's **Update and restart** control, permits one exact update attempt. An agent cannot supply
either response for the person. Verification with temporary installation data is permitted.
Required Celetis marketplace entries use `autoUpdate: false`. Valid recorded scopes authorize
refresh and removal, including manual edits inside an owned object key or dedicated whole file.
Show each replacement and removal before the existing commit-and-push question. Preserve
differing unowned entries and report their exact warnings for owner action. The command checks project settings only. Report that scope and each
known effective local, user, managed, or native policy conflict. Generated policy is not proof
that a host loaded it or that a stronger policy permits only confirmed updates. A project false
value does not override a managed true value.

Sessions and daemons may stay open. Discovery holds a short read lock and releases it before
foreground execution; only updaters serialize on the update mutex. Native replacement can remove
resources that open work still needs. The daemon that serves the board restarts itself after an
update approved in the board succeeds. A person may restart other affected work.
A fresh session loads changed skills; an existing session does not reload them automatically.

1. **The checkout.** Run in the main checkout of the product project, and enter no lane worktree. Run each call as `celetis --agent <host> setup <sub-command>`, with `<host>` the host that runs this session.
2. **The checks.** Run `check` before resolving any answer. If it fails, show its output and stop: an invalid present answer is a refusal, not a missing answer. A warning is no stop: keep it for the report. After a pass, the current branch is the trunk. Use only the validated `{"answers":{...}}` output for saved tracker and hosts; do not parse the record into arguments.
3. **The tracker.** Reuse a saved supported tracker. Ask which issue tracker the project uses only when the answer is absent or the invocation explicitly requests a change. On each answer other than GitHub, say that only GitHub is supported now, and stop.
4. **The hosts.** Reuse saved hosts and their order. Ask Claude, Codex, or both only when hosts are absent or the invocation explicitly requests a change that needs an answer; with both, resolve their priority order. Resolve the selection once and pass that same ordered selection to `try` and `write`. Get the values of `.celetis.yaml` of the main checkout once, here, from the reader CLI of the entry contract: steps 5, 6, and 12 use them, and with no file there are none. Run `celetis --agent <host> agents read`, show the current local order, and retain its order and version. The selected hosts configure project integration. Preserve an existing valid local preference and the tracked `agents` policy, including when the invocation selects one host. A separate explicit request naming an agent-order or policy change authorizes that different action. The selected order initializes only an absent local preference during `write`. Before completing setup, run `agents read` again: an existing valid preference must have its initial order and version. Run `celetis --agent <host> update check` once, and read the part of each chosen host. An installed part passes. A part with `error` is a warning that quotes its cause. A `skipped` part is a warning with the install commands of `<plugin>/README.md` ("Each machine") for that host. Neither warning is a stop.
5. **The landing.** Use the current validated `landing` as the answer. Only when it is absent or the invocation explicitly requests a change, resolve a new answer: use an explicit value, else read `.github/workflows/`. A PR check is a workflow whose `on` holds `pull_request` or `pull_request_target` with no `paths` or `paths-ignore` filter. A `branches` filter there must match the trunk, and a `branches-ignore` filter must not. Propose `pr` with one PR check or more, else `merge`, and ask the maintainer to confirm or change the proposal.
   With `merge`, use the current validated `suite` as the answer. Only when it is absent or explicitly requested to change, use an explicit new value, else propose the full suite that `AGENTS.md` names, else the verify gate that it names, and ask for the answer. The suite is a TypeScript file of the checkout, as a relative path. `land` runs it at the tip that it lands. With `pr`, ask for no suite. Pass the same resolved landing and suite to `try` and `write`.
6. **The proposal.** Make a scratch folder for the unchanged file inputs of `write`, such as the baseline section, with `mktemp -d "${TMPDIR:-/tmp}/celetis.XXXXXX"`, outside the checkout. Write those inputs with the file tools of the host, byte for byte. Remove the scratch folder at the end of step 9, also when the session stops before it. Application source stays in the product checkout. When `.celetis.yaml` has `worktreeSetup`, also `""`, keep it, propose no script, and go to step 7: the test runs the referenced lane file, and `""` is the maintainer's choice of no setup. Else read the manifests and lockfiles (for example `pyproject.toml`, `requirements*.txt`, `uv.lock`, `package.json` and its lockfile), the version pins (for example `.python-version`, `requires-python`, `.nvmrc`, `engines`, `.tool-versions`), and the CI workflows. With no manifest, propose no script, say so, and go to step 7. Else propose one normal TypeScript file, with a root-relative path such as `scripts/worktree-setup.ts` and its complete contents:
   - It is TypeScript on the selected Bun. Pass each external executable and its arguments as an array. Check each exit status and stop on failure; keep child streams inherited.
   - It gets the interpreter from a version manager that can fetch it, at the version that the project pins, and never uses the bare system interpreter. Check that version against the constraints of the dependencies. With `uv`, add `--managed-python`, because uv uses a system Python when the machine has no managed one.
   - It builds the environment inside the lane (`.venv/`, `node_modules/`), with an editable install in that environment, so the lane tests its own code.
   - It copies an ignored file from `process.argv[2]`, the absolute main checkout, only by its exact name. Each copy is optional: when its source is missing, the script prints one line on stderr and continues, because a failed setup removes the new lane. It copies no credential file: an `.env` file other than an example, a key or a certificate, a token file, or a path outside the checkout. To choose, list the ignored files of the main checkout by name only (`git status --ignored --porcelain`), and read no credential file.

   Show the path, the complete script, each copied file, each excluded credential path, each tool that each machine needs (for example `uv`), and the checks of the project (step 7, check 4). Ask the maintainer to approve or change the proposal. Then require the product owner to create the approved file and all required helpers and commit them on the local trunk in a separate product change before the detached wiring test. Report this precondition even when source creation is not authorized. If the file or a required helper is absent or not committed, name it and stop before `try`. Setup creates, copies, stages, owns, commits, and pushes no application source to make its test possible. Run the committed script only through `try` and `lane`.
7. **The test lane.** Confirm that the approved entry and required helpers are committed on the local trunk, with the entry's index and working file unchanged from HEAD. Run `try` with the options of `write` (step 9): the resolved answers of steps 4 and 5 (with `merge`, `--suite`), `--setup-file <path>` with the exact root-relative reference of a proposed script, and one `--ignore` for each approved line. The reference resolves from the main checkout root, also when the command starts in a subfolder. With no script, run `try` too: the test then shows a new lane with no setup. The setup can take minutes, so run `try` in the background, and wait for its end. Its stdout is the path of the test lane, also after a failed setup, and its exit status is the status of the setup. If it prints no path, show its output, run `try --remove`, and stop. Run each command of the test lane with that path as the working directory, and enter no lane with the worktree tools of the host. Check there:
   1. `setup try` exits 0.
   2. With a script, the import of the package of the project resolves to a path inside the test lane. For Python, run `<lane>/.venv/bin/python -c 'import <package>; print(<package>.__file__)'`, with `.venv/Scripts/python.exe` on Windows.
   3. With a script, each file that it copies is in the test lane when its source is in the main checkout: a copy with a wrong path prints only one line on stderr, and `setup try` still exits 0.
   4. Run the checks of the project: the verify gate that `AGENTS.md` names, else the steps of the CI workflows, else the lint, test, and type-check scripts of the manifests. Run only lint, test, type-check, and build steps that need no secret. Run a slow check in the background, and wait for its end. Record each failure: the command, the count, and a short summary. A failure from a missing environment or tool is a finding of the setup, not a failure of the base.
   5. `git status --porcelain --untracked-files=all` is empty after the setup and after the checks. For each untracked path of plain `git status --porcelain`, which shows a folder such as `node_modules/` as one line, propose a `.gitignore` line (for example `.venv/`, `.mypy_cache/`). A changed tracked file, for example a lockfile that the install wrote again, is a finding of the script, not an ignore line. After the maintainer's yes, run `try` again with the lines.
   6. Read each hook that Git runs at a commit or a push (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `pre-push`): in the folder of `git config core.hooksPath` when it is set, else in the folder that `git rev-parse --git-path hooks` prints, and each entry of `git config --get-regexp '^hook\.'`. Check each path that a hook resolves from the working directory (for example a tool in `.venv/bin/`), and each tool that it finds on `PATH`. Run the pre-commit hook in the test lane. The run alone is no proof: a hook can pass because nothing is staged. Record each hook that does not find a tool, or that skips its checks in the test lane. Leave each hook as it is.

   Each run of `try` makes a new test lane, so do the checks again after it. When check 1, 2, 3, or 5 fails for a proposed script, change the proposal with the maintainer. Require the owner to commit the changed entry and helpers on the local trunk in a separate product change before another `try`; uncommitted source is not copied into the test lane. Only a proposed reference that passed checks 1, 2, 3, and 5 goes to the write. When the maintainer drops the proposal, drop the results and the ignore lines of its test, and run `try` again with no proposed reference. When the reference was in `.celetis.yaml` already, a failure is a finding of the report, and the maintainer changes the field by hand. A missing tool is a finding too: name its install, and install no tool. When the checks are done, run `try --remove`.
8. **The baseline.** When check 4 found a failure of the base and `AGENTS.md` states no baseline rule, draft a section for `AGENTS.md`: the heading `## Baseline of the checks` on the first line, the rule to compare each check of a lane with the base commit of the lane, not with zero, and each failure with its command, its count, and the date of the test. Give a failure that needs a service or the network its cause. Ask the maintainer to approve or change the text, and write the approved section into a file of the scratch folder. When `AGENTS.md` states a baseline rule already, keep the new failures for a hand edit.
9. **The write.** Run `write --hosts claude|codex|claude,codex|codex,claude --landing pr|merge [--suite <file>] [--setup-file <path>] [--ignore <line>]... [--baseline-file <file>]` with the answers; `--suite` goes with `merge` only. The host order initializes only an absent local preference. Pass only the approved parts: `--setup-file` with the exact committed root-relative reference that passed its test, one `--ignore` for each approved line, and `--baseline-file` with the approved section. Setup writes the reference, not application source, and gains no ownership of that source. Every host selection also creates or refreshes the marked Celetis instruction block; `<plugin>/README.md`, "`AGENTS.md`", defines its boundary. If it fails, show its output, the failing path, `git status --short`, the complete diff of each changed or deleted setup path, and each new setup file in full. Report the partial writes and require the owner to review and commit or restore them before retry under the existing dirty-path guard. Claim no success, make no automatic push, and stop.
10. **The report.** Show the actual managed instruction path and complete block, also when no file changed. State that later setup runs replace text inside its markers and that project-specific instructions belong outside them. Show the output of `write`: the labels that it made, the warnings, and every changed or deleted path. Explain that valid recorded owned scopes are refreshed or removed, including manual edits inside owned keys and dedicated files; the resulting record drops retired claims. Shared files retain content outside those scopes. Quote each warning exactly and state its manual action. For each unresolved warning `setup: warning: .celetis.yaml: <key> is <value>, not <answer>; setup leaves it`, say that setup keeps the value of the file, and that the maintainer changes that field of `.celetis.yaml` by hand when the answer is the intended value. For `setup: warning: .celetis.yaml: worktreeSetup differs from the requested setup reference; setup leaves it` and `setup: warning: AGENTS.md: <heading> is there; setup leaves it`, say that setup keeps the value or text of the file, and that the maintainer edits it by hand when the approved reference or text is the intended one. Show each remaining caller path and the literal-search limit: dynamic or external references are not covered. For unowned old wiring or differing unowned rules, use `<plugin>/README.md`, "Review old wiring". For an unrelated instruction link or a wrong import, require owner review of that file and the required relative import. For an enabled or unknown automatic-update policy, require the owner to set the effective Celetis `autoUpdate` policy to false. Show the results of the test lane, the hook findings, the baseline section or the failures for a hand edit, each excluded credential path, and each tool that each machine needs. With any unresolved wiring or policy warning, do not say that the wiring is current, even with `setup: no file changed`. The no-change line describes the diff only and proves no native policy loading. With no changed path and no warning that the trunk is ahead of `origin`, go to step 12 with those limits. Else show the commits ahead of `origin`, which the push carries. With a changed path, also show:
    - `git status --short`;
    - the complete `git diff` of every changed or deleted path, and each new file in full;
    - each JSON formatting change, including in `.claude/settings.json`. JSON values outside the validated owned scopes and required additions stay unchanged; formatting can change. The rewrite can expand compact JSON, split an array on one line, change CRLF to LF, and add a missing final newline;
    - the parts of `AGENTS.md` that stay by hand: the verify gate, the architecture and the traps, and the acts that only the maintainer does (`<plugin>/README.md`, "`AGENTS.md`").

    Then ask one question: commit and push to `origin/<trunk>`? With no changed path, ask only to push.
11. **The push.** On a yes, run `push`. If it passes, show its output, `git log -1 --stat origin/<trunk>`, and `git status --short`. If it fails, show its output with the message of git; after `setup: the push failed`, say that the commit stays on the local trunk, and that a later run of this skill pushes it after the cause is fixed. When the message of git says that the trunk refuses direct pushes, say instead that the maintainer pushes the setup commit to a branch, lands it through a PR, and then runs `git pull --rebase` on the local trunk. After `setup: the commit failed`, say that the files stay uncommitted, and ask the push question again when the maintainer has fixed the cause. After a failed `push`, go to step 12, and stop after it. On a no with a changed path, say that the files stay uncommitted in the main checkout, and that the resolver stops on a dirty tree until the maintainer commits or drops them. When `write` added `worktreeSetup`, also say that a new lane gets no setup until the wiring is on the trunk of `origin`. On a no with no changed path, say that the commits ahead stay on the local trunk.
12. **The existing lanes.** Run this step also after a no to the push or a failed `push`. When the main `.celetis.yaml` has a `worktreeSetup` that is not empty (the value of step 4, else the reference that `write` added), list the lanes: each worktree of `git worktree list --porcelain` in `.claude/worktrees/` on a branch `feat|fix|hotfix|chore/<n>-*`. A prototype checkout is no lane. Ask for each lane whether to run the referenced file there now. On a yes, run `lane <path>` in the background, and wait for its end. Main selects the reference; the target lane supplies its file. If an older lane lacks that file or a required helper, report the exact missing path and require the owner to bring the committed source into that lane before retry. Copy no source and add no automatic merge or fallback. Show the output of a failed run. Then show `git status --short` with the lane path as the working directory, and continue with the next lane. Leave the lane as the run made it. Name each lane that the run made dirty: the resolver stops its issue on a dirty tree, and after the wiring is on the trunk, a merge of the trunk into its branch brings the ignore lines. End with the changed paths and each unresolved warning; keep the limits of step 10.
