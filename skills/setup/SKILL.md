---
name: setup
description: Writes the wiring of the plugin celetis into a product project. Only a human starts it.
disable-model-invocation: true
---

**Host entry.** Before any step or response, including commentary or an announcement, bind `<plugin>` to the absolute prefix before `/skills/<name>/SKILL.md` in this loaded file's path. Read [the host operations](../../docs/hosts/entry.md) at `<plugin>/docs/hosts/entry.md` directly, before any product-path scan. The relative link starts in the absolute directory containing this SKILL.md. Complete its startup reads on each invocation, including a same-session handoff.

The session asks the questions and holds setup approval; `setup` of the launcher makes each
change of the project. Setup approval is separate from a plugin update offer. Shared Host entry
owns the one-task update check and direct chat reply. New and unchanged old owned Celetis entries
use `autoUpdate: false`; show the precise proposed replacement before the existing write/push
decision. Leave unowned or independently changed entries for their owner. Report effective
local, project, user, managed, and native global policy conflicts and file-only coverage limits.
Stop affected consumers before any approved policy cutover, then require fresh sessions. A
project false value is no override of a managed true value; a successful setup write is no proof
of complete native resource lifetime.

1. **The checkout.** Run in the main checkout of the product project, and enter no lane worktree. The project can have no launcher yet, so run each call as `<plugin>/scripts/celetis --agent <host> setup <sub-command>`, with `<host>` the host that runs this session.
2. **The tracker.** Ask which issue tracker the project uses. On each answer other than GitHub, say that only GitHub is supported now, and stop.
3. **The checks.** Run `check`. If it fails, show its output and stop. A warning is no stop: keep it for the report. After a pass, the current branch is the trunk.
4. **The hosts.** Ask: Claude, Codex, or both. For each chosen host, run `<plugin>/scripts/celetis --agent <chosen> root`. A failure is a warning with the install commands of `<plugin>/README.md` ("Each machine") for that host, not a stop. With both hosts, ask which one is the default host of the bare terminal and board commands; when `.celetis.yaml` has `host`, propose that value as the default host.
5. **The landing.** When `.celetis.yaml` has `landing`, propose its value. Else read `.github/workflows/`. A PR check is a workflow whose `on` holds `pull_request` or `pull_request_target` with no `paths` or `paths-ignore` filter. A `branches` filter there must match the trunk, and a `branches-ignore` filter must not. Propose `pr` with one PR check or more, else `merge`. The maintainer confirms or changes it.
6. **The proposal.** Make a scratch folder for the input files of `write` with `mktemp -d "${TMPDIR:-/tmp}/celetis.XXXXXX"`, outside the checkout. Write each file there with the file tools of the host, byte for byte: the files go to `try` and `write` as files so that the shell does not change their text. Remove the scratch folder at the end of step 9, also when the session stops before it. When `.celetis.yaml` has `worktreeSetup`, also `""`, keep it, propose no script, and go to step 7: the test runs that script, and an empty one is the maintainer's choice of no setup. Else read the manifests and lockfiles (for example `pyproject.toml`, `requirements*.txt`, `uv.lock`, `package.json` and its lockfile), the version pins (for example `.python-version`, `requires-python`, `.nvmrc`, `engines`, `.tool-versions`), and the CI workflows. With no manifest, propose no script, say so, and go to step 7. Else propose one script:
   - It is TypeScript on the selected Bun. Pass each external executable and its arguments as an array. Check each exit status and stop on failure; keep child streams inherited.
   - It gets the interpreter from a version manager that can fetch it, at the version that the project pins, and never uses the bare system interpreter. Check that version against the constraints of the dependencies. With `uv`, add `--managed-python`, because uv uses a system Python when the machine has no managed one.
   - It builds the environment inside the lane (`.venv/`, `node_modules/`), with an editable install in that environment, so the lane tests its own code.
   - It copies an ignored file from `process.argv[2]`, the absolute main checkout, only by its exact name. Each copy is optional: when its source is missing, the script prints one line on stderr and continues, because a failed setup removes the new lane. It copies no credential file: an `.env` file other than an example, a key or a certificate, a token file, or a path outside the checkout. To choose, list the ignored files of the main checkout by name only (`git status --ignored --porcelain`), and read no credential file.

   Show the script, each copied file, each excluded credential path, each tool that each machine needs (for example `uv`), and the checks of the project (step 7, check 4). Ask the maintainer to approve or change the proposal, and write the approved script into a file of the scratch folder. Run the script only through `try` and `lane`.
7. **The test lane.** Run `try` with the options of `write` (step 9): the answers of steps 4 and 5, `--setup-file` with the file of a proposed script, and one `--ignore` for each approved line. With no script, run `try` too: the test then shows a new lane with no setup. The setup can take minutes, so run `try` in the background, and wait for its end. Its stdout is the path of the test lane, also after a failed setup, and its exit status is the status of the setup. If it prints no path, show its output, run `try --remove`, and stop. Run each command of the test lane with that path as the working directory, and enter no lane with the worktree tools of the host. Check there:
   1. The setup exits 0.
   2. With a script, the import of the package of the project resolves to a path inside the test lane. For Python, run `<lane>/.venv/bin/python -c 'import <package>; print(<package>.__file__)'`, with `.venv/Scripts/python.exe` on Windows.
   3. With a script, each file that it copies is in the test lane when its source is in the main checkout: a copy with a wrong path prints only one line on stderr, and the setup still exits 0.
   4. Run the checks of the project: the verify gate that `AGENTS.md` names, else the steps of the CI workflows, else the lint, test, and type-check scripts of the manifests. Run only lint, test, type-check, and build steps that need no secret. Run a slow check in the background, and wait for its end. Record each failure: the command, the count, and a short summary. A failure from a missing environment or tool is a finding of the setup, not a failure of the base.
   5. `git status --porcelain --untracked-files=all` is empty after the setup and after the checks. For each untracked path of plain `git status --porcelain`, which shows a folder such as `node_modules/` as one line, propose a `.gitignore` line (for example `.venv/`, `.mypy_cache/`). A changed tracked file, for example a lockfile that the install wrote again, is a finding of the script, not an ignore line. After the maintainer's yes, run `try` again with the lines.
   6. Read each hook that Git runs at a commit or a push (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `pre-push`): in the folder of `git config core.hooksPath` when it is set, else in the folder that `git rev-parse --git-path hooks` prints, and each entry of `git config --get-regexp '^hook\.'`. Check each path that a hook resolves from the working directory (for example a tool in `.venv/bin/`), and each tool that it finds on `PATH`. Run the pre-commit hook in the test lane. The run alone is no proof: a hook can pass because nothing is staged. Record each hook that does not find a tool, or that skips its checks in the test lane. Leave each hook as it is.

   Each run of `try` makes a new test lane, so do the checks again after it. When check 1, 2, 3, or 5 fails for a proposed script, change the proposal with the maintainer, and run `try` again. Only a proposed script that passed checks 1, 2, 3, and 5 goes to the write. When the maintainer drops the script, drop the results and the ignore lines of its test, and run `try` again with no script. When the script was in `.celetis.yaml` already, a failure is a finding of the report, and the maintainer changes the field by hand. A missing tool is a finding too: name its install, and install no tool. When the checks are done, run `try --remove`.
8. **The baseline.** When check 4 found a failure of the base and `AGENTS.md` states no baseline rule, draft a section for `AGENTS.md`: the heading `## Baseline of the checks` on the first line, the rule to compare each check of a lane with the base commit of the lane, not with zero, and each failure with its command, its count, and the date of the test. Give a failure that needs a service or the network its cause. Ask the maintainer to approve or change the text, and write the approved section into a file of the scratch folder. When `AGENTS.md` states a baseline rule already, keep the new failures for a hand edit.
9. **The write.** Run `write --hosts claude|codex|claude,codex [--default claude|codex] --landing pr|merge [--setup-file <file>] [--ignore <line>]... [--baseline-file <file>]` with the answers; `--default` goes with both hosts only. Pass only the approved parts: `--setup-file` with the script that passed its test, one `--ignore` for each approved line, and `--baseline-file` with the approved section. If it fails, show its output and `git status --short`, and stop.
10. **The report.** Show the output of `write`: the labels that it made, the warnings, and the changed paths. For each warning `setup: warning: .celetis.yaml: <key> is <value>, not <answer>; setup leaves it`, say that setup keeps the value of the file, and that the maintainer changes that field of `.celetis.yaml` by hand when the answer is the intended value. For `setup: warning: .celetis.yaml: worktreeSetup differs from the setup file; setup leaves it` and `setup: warning: AGENTS.md: <heading> is there; setup leaves it`, say that setup keeps the text of the file, and that the maintainer edits it by hand when the approved text is the intended one. Show the results of the test lane, the hook findings, the baseline section or the failures for a hand edit, each excluded credential path, and each tool that each machine needs. With `setup: no file changed` and no warning that the trunk is ahead of `origin`, the wiring is current: go to step 12. Else show the commits ahead of `origin`, which the push carries. With a changed path, also show:
    - `git status --short`;
    - the `git diff` of each changed path, and each new file in full;
    - a reflow of `.claude/settings.json` lines other than the added entries, when there is one: the JSON rewrite splits an array on one line, changes CRLF to LF, and adds a missing final newline;
    - the parts of `AGENTS.md` that stay by hand: the verify gate, the architecture and the traps, and the acts that only the maintainer does (`<plugin>/README.md`, "`AGENTS.md`").

    Then ask one question: commit and push to `origin/<trunk>`? With no changed path, ask only to push.
11. **The push.** On a yes, run `push`. If it passes, show its output, `git log -1 --stat origin/<trunk>`, and `git status --short`. If it fails, show its output with the message of git; after `setup: the push failed`, say that the commit stays on the local trunk, and that a later run of this skill pushes it after the cause is fixed. When the message of git says that the trunk refuses direct pushes, say instead that the maintainer pushes the setup commit to a branch, lands it through a PR, and then runs `git pull --rebase` on the local trunk. After `setup: the commit failed`, say that the files stay uncommitted, and ask the push question again when the maintainer has fixed the cause. After a failed `push`, go to step 12, and stop after it. On a no with a changed path, say that the files stay uncommitted in the main checkout, and that the resolver stops on a dirty tree until the maintainer commits or drops them. When `write` added `worktreeSetup`, also say that a new lane gets no setup until the wiring is on the trunk of `origin`. On a no with no changed path, say that the commits ahead stay on the local trunk.
12. **The existing lanes.** Run this step also after a no to the push or a failed `push`. When the main `.celetis.yaml` has a `worktreeSetup` that is not empty, list the lanes: each worktree of `git worktree list --porcelain` in `.claude/worktrees/` on a branch `feat|fix|hotfix|chore/<n>-*`. A prototype checkout is no lane. Ask for each lane whether to run the script there now. On a yes, run `lane <path>` in the background, and wait for its end. Show the output of a failed run. Then show `git status --short` with the lane path as the working directory, and continue with the next lane. Leave the lane as the run made it. Name each lane that the run made dirty: the resolver stops its issue on a dirty tree, and after the wiring is on the trunk, a merge of the trunk into its branch brings the ignore lines. When the wiring is current (step 10), say so, and end.
