# implement

Superset of `superpowers:subagent-driven-development` for project plans. Delegates to it; sets the capability tier of every dispatch + gates each task and a final verify phase.

## Do this

1. Enter the issue's worktree: run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'worktree' '<n>'` with a 10-minute timeout and bind the exact path it prints using the host operations (reuse the binding when the session is already there). The script re-enters the issue's branch, or creates it when the issue has none; when it refuses, show the user its message and stop. Then fetch the plan into `docs/superpowers/plans/<n>.md`. A hotfix's micro-plan is already there, written by its lane. Every other lane's plan is the latest `## Plan` comment on the issue, which a local file from the `plan` session can lag: `mkdir -p docs/superpowers/plans && gh issue view <n> --json comments --jq '[.comments[] | select(.body | startswith("## Plan"))][-1].body' > docs/superpowers/plans/<n>.md`.

   **Re-entry**, for each lane but a hotfix (its micro-plan is a local file): run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'state'` and read its lines (`<plugin>/docs/issue-tracker.md`, "Conventions"). Each `open:` line names a `## Before landing` comment of this build that has no completion evidence, and the evidence that is missing. `build: planned` is a plan to build. `build: built` means that an earlier run built the change. Do not build again: run no task of the plan, skip the Tail steps 1 to 4, and read the latest `## Landing refused` comment. When the change made the cause that the comment names, fix it as Land, step 4, says. When the cause is outside the change and the trunk now holds its fix, fetch the trunk from `origin`, merge it into the branch, and run the verify gate of the project, so that the checks run on a new head. Then go to Land, step 2. The exception is a `## Before landing` comment of this build that names an act of "During the build" with no report (the Verify phase below, or Land, step 2). When no `open:` line names that comment, and one or more `## Human steps done` comments after it report each act that it names, run the Verify scenarios that the comment names as waiting for those acts. Go to Land, step 2 on a PASS; a FAIL loops back to a fix, as in the Verify phase. Without that evidence, go to Land, step 2. `build: not-marked` and `build: added-again` come with a `stop` line: show the user that line, and stop. A new `/celetis:plan` run adds `ready-for-agent` again, so a new plan is built.
2. Invoke `superpowers:subagent-driven-development` using the host operations and follow it — it owns the per-task implementer and review loop, which findings you fix or rule on, and the final whole-branch review. Land (Tail step 5) takes the place of its last step, the skill that finishes the development branch: do not invoke that skill.
3. Layer the project additions below.

## Additions

**Capability tier — every dispatch.** Each task carries a `CAP: … → model/effort` line (plan scored it). Resolve its binding with `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'capscore' J V B N S X --bias BIAS --attempt N --json` through the host operations (`<plugin>/docs/capability.md`):
- Reuse the published six digits and bias (`+bN`; absent means `--bias 0`). Published model labels are history. Re-score only a task whose scope materially changed; changing hosts does not change its score.
- Apply both `dispatch.model` and `dispatch.effort` with the host's actual controls; put `line` FIRST in the child prompt and record the pair and child identity. Keep the parent model. A CAP line alone does not configure a child.
- The **task reviewer uses the implementer's score and attempt with `--reviewer`**, applying the host's reviewer minimum. No separate task-review score; the scorer owns its floors and clamp.
- Each child receives the exact lane path, relevant project instructions, its task and constraints, and required skill/custom text through the host operations. Retain the same implementer for repairs and the same reviewer for scoped re-review. If the required pair cannot be applied to that identity, stop for setup with the failure trail.

**Comment policy — append to every implementer prompt (verbatim):**
> Comments: default none; one line only for a constraint the code can't show; never narrate what the next line does or why the change is correct. Style source: the `celetis:polishing-code-comments` skill.

**Commit subject — append to every implementer prompt (verbatim):**
> Commit subject: `<type>(<area>): <what>` — `<area>` is whatever a reader would recognise: the package or concern the task touched (`lib` alone if nothing is clearer). `<type>` is `feat` for new behavior, else `fix`/`refactor`/`test`. Body: what changed and why, naming a symbol a reader can grep, and referencing `#<n>`.

**Gate each task before its review.** The base loop is implementer → task review; insert a deterministic gate between them:
1. Implementer returns DONE → run the verify gate of the project.
2. **Pass** → dispatch the task reviewer.
3. **Fail** → re-dispatch the *implementer* (not the reviewer) with the `GATE FAIL: <name>` + the report path + a re-resolved tier from `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'capscore' J V B N S X --bias BIAS --attempt N --json` through the host operations. The orchestrator owns N per task (session-scoped): attempt 2 → +1 effort · attempt 3 → +1 model · **attempt 4 → STOP, escalate to the user with the failure trail.**

**Tail — after every task is review-clean, in order:**
1. `celetis:polishing-code-comments` sweep over the full branch diff (once per branch).
2. Broad final whole-branch review (base skill's final review), scored as its own dispatch with `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'capscore'`: add `--reviewer` and apply the resolved host pair in place of the upstream "most capable model" (`<plugin>/docs/capability.md`).
3. A re-run of the verify gate of the project.
4. The **Verify phase** (below) — its PASS/FAIL is a hard gate.
5. **Land** — `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'land'` puts the change on the trunk by `landing` in `.celetis.yaml` (ADR-0008 of the plugin `celetis`). It is the one landing path of an agent.
   1. Run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'state'`. With `build: planned`, run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'built'`: the removal of `ready-for-agent` after the latest `## Plan` comment is the mark that the change is built. With another `build:` (`none` in a hotfix, or `built` when the change has its mark), go on to step 2.
   2. **Human precondition.** An act of "During the build" in `### Your steps` of the plan is done when a `## Human steps done` comment after the latest `## Plan` comment reports it. When the change needs an act that only a human can do before it reaches the trunk, no such report holds the act, and either the issue has no `## Before landing` comment for this build or the act is an act of "During the build" that no such comment names: write a file with no heading that names each such act, with the report form of each act of "During the build", run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'before-landing' '<file>'`, with `'--during-the-build'` after the file when it names an act of "During the build", and stop. The command posts the file with `## Before landing` as its first line, then adds `ready-for-human`. The maintainer completes the act and clears the label. Before landing on re-entry, read the `open:` lines of `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'state'`: the engine reads the completion evidence of each `## Before landing` comment of this build from the issue timeline (`<plugin>/docs/issue-tracker.md`, "Completing a human precondition"). An absent label is not completion evidence. The engine reads that a `## Human steps done` comment exists, not which acts it reports. So with an `open:` line, or with a `## Before landing` comment of this build that names an act of "During the build" that no later `## Human steps done` comment reports, keep the change built, restore the label with `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'ready-for-human'`, using the existing comment as the reason, and stop. With `open: none` and a report of each such act, continue to step 3.
   3. **The landing.** The full suite runs once, on the tree that lands, so the session runs no full suite before `land`: with the landing `merge`, `land` runs the `suite` file of `.celetis.yaml` in the lane, at the tip that it lands; with the landing `pr`, the CI of the lane PR runs it. Return to the main checkout using the host operations, keeping the lane. Run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'land' '<n>' '<type>(<area>): <what>'` there with the host's command spelling and background/session support, and go on when it ends: the checks and one re-run of a failed check can take 30 minutes. Keep its session identifier and wait for the exit; a yield or timeout is not completion. The subject is the squash subject of the change, without the issue number: the script adds ` (#<n>)`. When the lane branch holds one commit, pass the subject of that commit: the squash commit can take the subject of that commit in place of the argument. The exit status gives the result (`<plugin>/docs/celetis-flow.md`, "A landing", gives each class):
      - **0** ends the step: the change is on the trunk, and the worktree and the branch are gone. **An act of the maintainer** (each `land:` line other than `land: #<n> is on <trunk>` and `land: <branch> and its worktree are gone`, for example `land: the main checkout did not move to origin/<trunk>; run git pull on <trunk> there`) is no stop: quote each such line verbatim in the last message of the step, run no command for it, and post no comment and add no label for it. **A check by hand** (an item of "After the landing" in `### Your steps` of the plan) is no stop either: quote that list verbatim in the last message of the step, after the quoted `land:` lines, run no command for it, and post no comment and add no label for it.
      - **2** (`usage`) is **an error that the session caused** (the usage line, a run from inside the lane worktree, a lane worktree that is dirty). It is no refusal, and step 5 does not count it: correct it, and run the script again. A second 2 with the same line is a cause outside the change (step 5).
      - **3** (`prerequisite`): the issue is not ready to land, and the line quotes the line of the resolver. Run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'state'`. When its `line:` is `run /celetis:implement #<n>` with `build: planned`, step 1 did not complete: go to step 1. Each other `line:` is a stop: show the user the output, and stop. In a step session, rule 4 of `step-prompt.md` of the plugin `celetis` hands it to the issue with a `## Stopped` comment: the `## Landing refused` comment of step 5 needs a landing step on that line.
      - **4** (`repair`) is a refusal that the change caused: step 4.
      - **5** (`checks`) is a red check or a failed suite. Decide whether the diff caused it: step 4 when it did, else step 5.
      - **6** (`blocked`) and **1** are causes outside the change: step 5.
      - **7** (`cleanup`) is **a stop after the landing** (a `land:` line that says `run /usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'land' again`). It is no refusal, and step 5 does not count it: the change is on the trunk, so do what the line says and run the script again. A second 7 with the same line is a cause outside the change (step 5).
      - **128+n** is **a signal that stopped `land`** before it put the change on the trunk, for example the time limit of a background `land`. It is no refusal, and step 5 does not count it: run the script again once. A second 128+n is a cause outside the change (step 5).
   4. **A refusal that the change caused** (status 4, or a status 5 that the diff caused, before the change is on the trunk): a check or the suite that fails on the diff, a conflict with the trunk, a branch that does not contain the trunk head, a trunk head or a lane tip that changed during the landing. Enter the worktree again (`/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'worktree' '<n>'`, then bind its exact path through the host operations), fix the cause through the task loop (implementer, the verify gate of the project, task review), commit, and go to step 3. The loop is the task loop of `superpowers:subagent-driven-development`, with the fix as its one task: a session that did not invoke that skill invokes it now, for its task loop only. Debug a red check or a failed suite with `superpowers:systematic-debugging`, and start from the test that failed in CI or in the suite. Fix a conflict or a stale branch with a merge of the trunk into the branch.
   5. **The third refusal in one session, or a cause outside the change** (status 6 or 1, a status 5 that the diff did not cause, a second 2 or 7 with the same line, or a second 128+n): a check that fails on an advisory for a dependency that the change did not touch, no check that ran, checks that did not finish, GitHub that does not answer, a main checkout that is dirty or off the trunk. Write the output of the script to a file in the temporary directory from the host operations, run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'landing-refused' '<file>'`, which posts it with `## Landing refused` as its first line, show the user the output, and stop. Do not pass the output as a quoted argument: a message of `gh` can hold a backtick, and the shell runs it inside double quotes.

**Verify phase — prove the plan's Verify scenarios on the project's own runtime.** Execute the plan's Verify phase per the project's runtime shape (on-device for an app, a browser flow for web, a script for a backend). The phase runs no full suite: the CI of the lane PR runs it with the landing `pr`, and `land` runs it with the landing `merge` (Land step 3). A scenario that needs an act of "During the build" reads the value of the act from a `## Human steps done` comment after the latest `## Plan` comment. With no report of the act, the scenario cannot run and has no PASS: run each other scenario, then write one `## Before landing` comment for this build to a file, with no heading. It names each act with no report, its report form, and the scenarios that wait for it, not the commands of a scenario that waits for an act. In a step session, it also holds each scenario that a guard refused (rule 5 of `step-prompt.md` of the plugin `celetis`). Then run `/usr/bin/env BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 DO_NOT_TRACK=1 '<bun>' '--no-env-file' '--no-install' '--config=/dev/null' '--no-macros' '<plugin>/bin/celetis.ts' '--agent' '<host>' 'issue' '<n>' 'before-landing' '<file>' '--during-the-build'` as the last act, and stop. It posts the comment with the marker of an act of "During the build", then adds `ready-for-human` and removes `ready-for-agent`. A session never writes a `## Human steps done` comment.

A FAIL loops back to a fix subagent (same CAP tier), not to Land. (The Tail above sequences this phase; its PASS is the hard gate before Land.)

**TDD stays** the implementer loop.
