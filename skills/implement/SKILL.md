# implement

Superset of `superpowers:executing-plans` (the inline flow) and `superpowers:subagent-driven-development` (the subagent flow) for project plans. The `Execution:` line of the plan picks the flow. This skill gets each task-loop dispatch from `dispatch`, gates each task, and adds the Verify phase and the landing.

## Do this

1. Enter the issue's worktree: run `celetis --agent <host> worktree <n>` with a 10-minute timeout and bind the exact path it prints using the host operations (reuse the binding when the session is already there). The script re-enters the issue's branch and brings it up to the trunk, or creates it when the issue has none; when it refuses, show the user its message and stop. Then fetch the plan into `docs/superpowers/plans/<n>.md`. A hotfix's micro-plan is already there, written by its lane. Every other lane's plan is the latest `## Plan` comment on the issue, which a local file from the `plan` session can lag: `mkdir -p docs/superpowers/plans && gh issue view <n> --json comments --jq '[.comments[] | select(.body | startswith("## Plan"))][-1].body' > docs/superpowers/plans/<n>.md`.

   **Re-entry**, for each lane but a hotfix (its micro-plan is a local file): run `celetis --agent <host> issue <n> state` and read its lines (`<plugin>/docs/issue-tracker.md`, "Conventions"). Each `open:` line names a `## Before landing` comment of this build that has no completion evidence, and the evidence that is missing. `build: planned` is a plan to build. `build: built` means that an earlier run built the change. Do not build again: run no task of the plan, skip the Tail steps 1 to 4, and read the latest `## Landing refused` comment. When the change made the cause that the comment names, fix it as Land, step 4, says. When the cause is outside the change and the trunk now holds its fix, step 1 brought the trunk into the branch: run the verify gate of the project, so that the checks run on a new head. Then go to Land, step 2. The exception is a `## Before landing` comment of this build that names an act of "During the build" with no report (the Verify phase below, or Land, step 2). When no `open:` line names that comment, and one or more `## Human steps done` comments after it report each act that it names, run the Verify scenarios that the comment names as waiting for those acts. Go to Land, step 2 on a PASS; a FAIL loops back to a fix, as in the Verify phase. Without that evidence, go to Land, step 2. `build: not-marked` and `build: added-again` come with a `stop` line: show the user that line, and stop. A new `/celetis:plan` run adds `ready-for-agent` again, so a new plan is built.
2. **Read the flow.** Do this step with `build: planned`, or with a hotfix micro-plan. The plan names its flow on a line of the form `Execution: inline — <one-sentence reason>` or `Execution: subagent — <one-sentence reason>`. Read the first line of the plan file that starts with `Execution: `. The first word after `Execution: `, after any more spaces and up to the next space or the end of the line, is the flow: `Execution:    inline — …` is `inline`. No such line, or a word other than `inline` or `subagent`, is an invalid line. An invalid line stops `implement` before the first task: show the user this message, with `<n>` and `<found>` filled in, and stop. `<found>` is the first line that starts with `Execution: `, or `none`.
   - A plan from the issue: `implement: the plan of #<n> has no valid Execution: line (found: <found>). Run /celetis:plan #<n> again; the new plan names the build flow.`
   - A hotfix micro-plan: `implement: the micro-plan of #<n> has no valid Execution: line (found: <found>). Write Execution: inline — one task as its first line (step 5 of /celetis:hotfix), then run /celetis:implement #<n>.`

   In a step session, rule 4 of `step-prompt.md` of the plugin `celetis` hands the stop to the issue. Re-entry with `build: built` reads no line, so a built change lands with any plan.
3. Invoke `superpowers:executing-plans` for `inline`, or `superpowers:subagent-driven-development` for `subagent`, using the host operations, and follow it. The upstream skill owns its task loop, its final whole-branch review, and the fix pass of that review. With `executing-plans`, the session fixes the Critical and Important findings in one pass, each fix test-first, with no second review. The verify gate of the project takes the place of its whole-suite run (Land, step 3). With `subagent-driven-development`, one fix subagent fixes the findings, and one scoped re-review reads the fix. Land (Tail step 5) takes the place of its last step, the skill that finishes the development branch: do not invoke that skill.
4. Layer the project additions below: **Both flows**, and the group of the flow of the plan.

## Additions

### Both flows

**Task dispatch — every child in the subagent task loop and fixes after the final review.** Get each dispatch through the host operations with `celetis --agent <host> dispatch <act and arguments>`. The acts and their arguments are:

| Act and arguments | When to use it |
| --- | --- |
| `next <n> <task> implementer\|reviewer J V B N S X --bias N` | For the first dispatch of a role, an answer to a child's question, or a retry after an accepted report that no worker started. |
| `report <dispatch-id> <report-file>` | After each issued native call, before the next engine act. Use the execution report of the selected host. |
| `gate <n> <task> pass\|fail <gate> <report>` | After each implementer `DONE`, with the gate name and the report path. |
| `review <n> <task> findings` | After a task review reports spec ❌, a Critical finding, or an Important finding. |
| `review <n> <task> blocked` | After an implementer reports `BLOCKED`. |
| `close <n> <task>` | When the task review is clean. |

- For `next`, reuse the published six digits and bias (`+bN`; absent means `--bias 0`). Published model labels are history. Re-score only when the task scope changed. The task reviewer takes the digits and bias of its task; the engine applies the reviewer rules. Score each new task.
- Use the plan task number as `<task>`. Use `final` for the whole-branch review and its fix wave, `verify-<k>` for a fix after a Verify FAIL, and `land-<k>` for a fix of Land, step 4. Use a new positive `<k>` for each new fix task; repairs of that task keep its ID.
- On `status: "ready"`, put `line` first in the child prompt. Apply `pair.model` and `pair.effort` with the host's actual spawn controls; omit the model field when it is null. Keep the parent model and effort. A CAP line alone does not configure a child. Follow `action`: `spawn` starts a child; `resume` sends to `child` with the host's follow-up tool; `replace` starts a fresh child in place of the prior child of that role. Record the applied arguments and child identity. A resume retains the recorded pair; when the tool cannot apply the required pair, stop for setup with the reason and failure trail.
- Send each returned `ready` dispatch once. Save the exact tool name, arguments, and native result in an execution report, then run `report <dispatch-id> <report-file>` before the next engine act. Follow the selected host's report examples in the host operations. Each execution is agent-reported; the engine validates the report, not the native call. It cannot prevent an incorrect call or prove an internally consistent report true.
- An acknowledgment with `status: "reported"` issues no child. Wait for the child's real completion before its gate or review result. A gate pass already issues the reviewer; send that returned action once. Keep no second dispatch for it.
- Only an accepted `failed` report with `noWorkerStarted: true` permits `next` to retry that role. The retry names and voids the failed dispatch without changing its attempt or round. An uncertain error or missing identity stays incomplete; a mismatch stays a setup stop. For a missing follow-up operation, report `call: null` with outcome `unsupported` and the exact limitation, then stop. Use the host's command approval procedure for a sandbox block.
- Exit 3: correct the act that the reason names. Exit 4 or 5: stop with the reason and trail. In a step session, use rule 4 of `step-prompt.md` of the plugin `celetis`.
- These acts replace the round count, model choice, and "most capable model" procedure of `superpowers:subagent-driven-development`. Keep no attempt or round count in the ledger. The engine's stop after round 5 replaces the breaker of the upstream fix loop (`<plugin>/docs/capability.md`, "Dispatch records").
- Give each isolated child the exact lane path, relevant project instructions, its task and constraints, and required skill/custom text through the host operations.

**Comment policy — append to every implementer prompt (verbatim):**
> Comments: default none; one line only for a constraint the code can't show; never narrate what the next line does or why the change is correct. Style source: the `celetis:polishing-code-comments` skill.

**Commit subject — append to every implementer prompt (verbatim):**
> Commit subject: `<type>(<area>): <what>` — `<area>` is whatever a reader would recognise: the package or concern the task touched (`lib` alone if nothing is clearer). `<type>` is `feat` for new behavior, else `fix`/`refactor`/`test`. Body: what changed and why, naming a symbol a reader can grep, and referencing `#<n>`.

On the inline flow, the session builds each task itself and applies both blocks to its own work.

**TDD** is the method of each task.

**The verify gate of the project at the end of each task.** On the inline flow, the third failed gate of one task stops the session with the failure trail. On the subagent flow, the engine owns escalation and stops. In a step session, rule 4 of `step-prompt.md` of the plugin `celetis` hands the stop to the issue.

**Tail — after every task is review-clean, in order:**
1. `celetis:polishing-code-comments` sweep over the full branch diff (once per branch).
2. Broad final whole-branch review (the final review of the upstream skill):
   - On the inline flow, score the whole branch with `celetis --agent <host> capscore J V B N S X --bias BIAS --attempt 1 --reviewer --json`. Apply `dispatch.model` and `dispatch.effort` with the host's actual controls; put `line` first in the prompt and record the pair and child identity. Omit the model field when it is null. Keep the parent model and effort. Give the reviewer the exact lane path, full diff, relevant instructions, and required skill/custom text through the host operations. The session fixes Critical and Important findings in one pass, each fix test-first, with no second review.
   - On the subagent flow, score the whole branch, then run `celetis --agent <host> dispatch next <n> final reviewer J V B N S X --bias N`. Send findings to `review <n> final findings`; its returned action starts the one fix wave. After each implementer `DONE`, run the gate and report it with `gate`; on a pass, the engine issues the scoped re-review. Apply the upstream skill's rulings for each residual finding, then use `close <n> final`.
3. A re-run of the verify gate of the project.
4. The **Verify phase** (below) — its PASS/FAIL is a hard gate.
5. **Land** — `celetis --agent <host> land` puts the change on the trunk by `landing` in `.celetis.yaml` (ADR-0008 of the plugin `celetis`). It is the one landing path of an agent.
   1. Run `celetis --agent <host> issue <n> state`. With `build: planned`, run `celetis --agent <host> issue <n> built`: the removal of `ready-for-agent` after the latest `## Plan` comment is the mark that the change is built. With another `build:` (`none` in a hotfix, or `built` when the change has its mark), go on to step 2.
   2. **Human precondition.** An act of "During the build" in `### Your steps` of the plan is done when a `## Human steps done` comment after the latest `## Plan` comment reports it. When the change needs an act that only a human can do before it reaches the trunk, no such report holds the act, and either the issue has no `## Before landing` comment for this build or the act is an act of "During the build" that no such comment names: write a file with no heading that names each such act, with the report form of each act of "During the build", run `celetis --agent <host> issue <n> before-landing <file>`, with `--during-the-build` after the file when it names an act of "During the build", and stop. The command posts the file with `## Before landing` as its first line, then adds `ready-for-human`. The maintainer completes the act and clears the label. Before landing on re-entry, read the `open:` lines of `celetis --agent <host> issue <n> state`: the engine reads the completion evidence of each `## Before landing` comment of this build from the issue timeline (`<plugin>/docs/issue-tracker.md`, "Completing a human precondition"). An absent label is not completion evidence. The engine reads that a `## Human steps done` comment exists, not which acts it reports. So with an `open:` line, or with a `## Before landing` comment of this build that names an act of "During the build" that no later `## Human steps done` comment reports, keep the change built, restore the label with `celetis --agent <host> issue <n> ready-for-human`, using the existing comment as the reason, and stop. With `open: none` and a report of each such act, continue to step 3.
   3. **The landing.** The full suite runs once, on the tree that lands, so the session runs no full suite before `land`: with the landing `merge`, `land` runs the `suite` file of `.celetis.yaml` in the lane, at the tip that it lands; with the landing `pr`, the CI of the lane PR runs it. Return to the main checkout using the host operations, keeping the lane. Run `celetis --agent <host> land <n> '<type>(<area>): <what>'` there with the host's command spelling and background/session support, and go on when it ends: the checks and one re-run of a failed check can take 30 minutes. Keep its session identifier and wait for the exit; a yield or timeout is not completion. The subject is the squash subject of the change, without the issue number: the script adds ` (#<n>)`. When the lane branch holds one commit, pass the subject of that commit: the squash commit can take the subject of that commit in place of the argument. The exit status gives the result (`<plugin>/docs/celetis-flow.md`, "A landing", gives each class):
      - **0** ends the step: the change is on the trunk, and the worktree and the branch are gone. **An act of the maintainer** (each `land:` line other than `land: #<n> is on <trunk>` and `land: <branch> and its worktree are gone`, for example `land: the main checkout did not move to origin/<trunk>; run git pull on <trunk> there`) is no stop: quote each such line verbatim in the last message of the step, run no command for it, and post no comment and add no label for it. **A check by hand** (an item of "After the landing" in `### Your steps` of the plan) is no stop either: quote that list verbatim in the last message of the step, after the quoted `land:` lines, run no command for it, and post no comment and add no label for it.
      - **2** (`usage`) is **an error that the session caused** (the usage line, a run from inside the lane worktree, a lane worktree that is dirty). It is no refusal, and step 5 does not count it: correct it, and run the script again. A second 2 with the same line is a cause outside the change (step 5).
      - **3** (`prerequisite`): the issue is not ready to land, and the line quotes the line of the resolver. Run `celetis --agent <host> issue <n> state`. When its `line:` is `run /celetis:implement #<n>` with `build: planned`, step 1 did not complete: go to step 1. Each other `line:` is a stop: show the user the output, and stop. In a step session, rule 4 of `step-prompt.md` of the plugin `celetis` hands it to the issue with a `## Stopped` comment: the `## Landing refused` comment of step 5 needs a landing step on that line.
      - **4** (`repair`) is a refusal that the change caused: step 4.
      - **5** (`checks`) is a red check or a failed suite. Decide whether the diff caused it: step 4 when it did, else step 5.
      - **6** (`blocked`) and **1** are causes outside the change: step 5.
      - **7** (`cleanup`) is **a stop after the landing** (a `land:` line that says `run celetis --agent <host> land again`). It is no refusal, and step 5 does not count it: the change is on the trunk, so do what the line says and run the script again. A second 7 with the same line is a cause outside the change (step 5).
      - **128+n** is **a signal that stopped `land`** before it put the change on the trunk, for example the time limit of a background `land`. It is no refusal, and step 5 does not count it: run the script again once. A second 128+n is a cause outside the change (step 5).
   4. **A refusal that the change caused** (status 4, or a status 5 that the diff caused, before the change is on the trunk): a check or the suite that fails on the diff, a conflict with the trunk, a branch that does not contain the trunk head, a trunk head or a lane tip that changed during the landing. Enter the worktree again (`celetis --agent <host> worktree <n>`, then bind its exact path through the host operations), score a new `land-<k>` task, fix the cause through the dispatch task loop above (implementer, the verify gate of the project, task review, and `close`), commit, and go to step 3. The loop is the task loop of `superpowers:subagent-driven-development`, with the fix as its one task: a session that did not invoke that skill invokes it now, for its task loop only, with the dispatch additions above. Debug a red check or a failed suite with `superpowers:systematic-debugging`, and start from the test that failed in CI or in the suite. For a stale branch or a moved trunk, the `worktree` entry brought the trunk in: run the verify gate of the project, then go to step 3. When the entry refuses, for example on a conflict with the trunk, show the user its message and stop.
   5. **The third refusal in one session, or a cause outside the change** (status 6 or 1, a status 5 that the diff did not cause, a second 2 or 7 with the same line, or a second 128+n): a check that fails on an advisory for a dependency that the change did not touch, no check that ran, checks that did not finish, GitHub that does not answer, a main checkout that is dirty or off the trunk. Write the output of the script to a file in the temporary directory from the host operations, run `celetis --agent <host> issue <n> landing-refused <file>`, which posts it with `## Landing refused` as its first line, show the user the output, and stop. Do not pass the output as a quoted argument: a message of `gh` can hold a backtick, and the shell runs it inside double quotes.

**A fix after the final review.** A Verify FAIL and a refusal that the change caused (Land, step 4) use one rule in both flows. The rule needs no `Execution:` line, so it also works on re-entry. The fix runs the task loop of `superpowers:subagent-driven-development` with the fix as its one task: an implementer, the verify gate of the project, a task review, and `close`. The loop follows **Task dispatch** and **Gate each task before its review**. A session that did not invoke that skill invokes it now, for its task loop only. The plan has no task for the fix, and a clean final review deletes the plan's workspace. So the session writes the fix brief to a file in the workspace that `sdd-workspace PLAN_FILE` of that skill prints. The brief holds the cause (the failed scenario and its output, or the `land:` lines), the Global Constraints of the plan (for a micro-plan, the constraints of its task), and the verify gate of the project. The session scores the fix as a new `verify-<k>` or `land-<k>` task; no published digits exist for it. The task reviewer takes that task's digits and bias through the engine. It gets the brief, the report, and a review package over the fix range. No review follows such a fix, so its task review is its only review.

**Verify phase — prove the plan's Verify scenarios on the project's own runtime.** Execute the plan's Verify phase per the project's runtime shape (on-device for an app, a browser flow for web, a script for a backend). The phase runs no full suite: the CI of the lane PR runs it with the landing `pr`, and `land` runs it with the landing `merge` (Land step 3). A scenario that needs an act of "During the build" reads the value of the act from a `## Human steps done` comment after the latest `## Plan` comment. With no report of the act, the scenario cannot run and has no PASS: run each other scenario, then write one `## Before landing` comment for this build to a file, with no heading. It names each act with no report, its report form, and the scenarios that wait for it, not the commands of a scenario that waits for an act. In a step session, it also holds each scenario that a guard refused (rule 5 of `step-prompt.md` of the plugin `celetis`). Then run `celetis --agent <host> issue <n> before-landing <file> --during-the-build` as the last act, and stop. It posts the comment with the marker of an act of "During the build", then adds `ready-for-human` and removes `ready-for-agent`. A session never writes a `## Human steps done` comment.

A FAIL starts a new scored `verify-<k>` task through the dispatch task loop above (implementer, the verify gate of the project, task review, and `close`). Then run the failed scenarios again. The Tail above sequences this phase; its PASS is the hard gate before Land.

### Subagent flow only

**Capability tier of each task.** Each task carries a `CAP: … → model/effort` line (plan scored it). Use its digits and bias with **Task dispatch** above; the engine resolves the implementer and reviewer pairs.

**Gate each task before its review.** The base loop is implementer → task review; insert a deterministic gate between them:
1. Implementer returns `DONE` → run the verify gate of the project and save its report.
2. Report the result with `celetis --agent <host> dispatch gate <n> <task> pass|fail <gate> <report>`.
3. Send the returned `ready` dispatch once. A pass returns the task reviewer; a fail returns the implementer for repair. Include `GATE FAIL: <name>` and the report path in the repair prompt. The engine owns escalation and stops. After review findings or `BLOCKED`, use the corresponding `review` act; after a clean review, use `close`.

### Inline flow only

**The verify gate of the project is the test command of `task-done`.** End each task with `scripts/task-done PLAN_FILE N BASE -- <the verify gate of the project>` of `superpowers:executing-plans`. A task is complete only when the gate passes. `task-done` runs the command with no shell. A gate that starts with variable assignments starts with `/usr/bin/env`. A gate with a shell operator (`&&`, `;`, a pipe, a redirection) runs as `/bin/sh -c '<the verify gate of the project>'`.

**A failed gate** goes to `superpowers:systematic-debugging`, a fix, and a new run of `task-done`. Nothing raises the model or the effort, because no child runs.

**The CAP line of each task** is a recommendation for the session model.
